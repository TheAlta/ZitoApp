# Zito Database V2 - Canonical Design

Status: proposed canonical baseline; migration requires explicit final approval  
Date: 2026-07-28  
Scope: identity, profile, course publishing, 20 learning templates, course-scoped KB/RAG, runtime AI supervision, progress, legacy migration and rollback  

This document is the database source of truth for the next implementation step. It does not mean that the migration has already been executed.

## 1. Confirmed Product Decisions

1. `users.display_name` is the only user-facing name.
2. `display_name` is not unique.
3. `users.full_name`, `users.username` and `users.profession` are not part of the final schema.
4. PostgreSQL generates the user ID. No manual counter table is used.
5. A user is created only after successful OTP verification.
6. Removing a user from the admin panel is a soft delete: `users.deleted_at` is filled and the row remains.
7. A soft-deleted phone cannot create a second user row. The account must be restored or permanently anonymized through an explicit operation.
8. Profile information has a one-to-one relationship with `users`.
9. `user_profiles.user_id` is both the primary key and a foreign key to `users.id`.
10. The active learning engine uses the published course version and its 20 stored stage contents.
11. The CMS content-generation AI and the runtime supervisor AI are separate use cases.
12. Runtime RAG is restricted to the learner's enrolled course version and current stage tags.
13. Legacy tables are not dropped in the first migration. They are migrated, made read-only, observed, and removed later.

## 3. Identity Model

### 3.1 `users`

```text
users
-----
id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
phone               VARCHAR(20) NOT NULL
display_name        VARCHAR(100) NOT NULL
phone_verified_at   TIMESTAMPTZ NOT NULL
last_login_at       TIMESTAMPTZ NULL
created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
deleted_at          TIMESTAMPTZ NULL
```

Constraints and indexes:

```text
PRIMARY KEY (id)
UNIQUE (phone)
INDEX ix_users_deleted_at (deleted_at)
INDEX ix_users_display_name (display_name) only if admin search requires it
```

Rules:

- `id` is the internal immutable identity.
- Sequence values can have gaps. A gap is not an error and deleted IDs are never reused.
- `phone` remains unique even after soft delete.
- Phone normalization remains the current Iranian mobile format (`09xxxxxxxxx`) during this migration. International E.164 support is a separate product decision.
- `display_name` can contain any non-empty name accepted by the product and is not used for authentication.
- Normal application queries must include `deleted_at IS NULL`.
- Soft-deleted users cannot log in automatically.
- Restore is an explicit admin operation that sets `deleted_at = NULL`.
- Permanent deletion is a separate anonymization workflow, not the normal admin delete action.

### 3.2 User soft delete behavior

Admin delete:

```sql
UPDATE users
SET deleted_at = NOW(),
    updated_at = NOW()
WHERE id = :user_id
  AND deleted_at IS NULL;
```

Admin restore:

```sql
UPDATE users
SET deleted_at = NULL,
    updated_at = NOW()
WHERE id = :user_id
  AND deleted_at IS NOT NULL;
```

Expected API behavior:

- Active application routes treat a deleted user as unavailable.
- Admin list excludes deleted users by default.
- Admin list can explicitly request deleted users.
- Admin delete never calls `db.delete(user)`.
- Related profile, enrollment, stage progress, exam and certificate rows remain intact.

### 3.3 `user_sessions`

The current localStorage `user_id` mechanism is not authorization. OTP verification must create a user session.

```text
user_sessions
-------------
id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
user_id          BIGINT NOT NULL FK -> users.id ON DELETE CASCADE
token_hash       CHAR(64) NOT NULL UNIQUE
created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
expires_at       TIMESTAMPTZ NOT NULL
last_seen_at     TIMESTAMPTZ NULL
revoked_at       TIMESTAMPTZ NULL
ip_hash          CHAR(64) NULL
user_agent       VARCHAR(500) NULL
```

Indexes:

```text
UNIQUE (token_hash)
INDEX ix_user_sessions_user_active (user_id, revoked_at, expires_at)
```

Rules:

- The browser receives an opaque session token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie.
- Only the hash is stored in the database.
- User APIs derive `user_id` from the session; they do not accept arbitrary ownership through a query parameter.
- Soft deleting a user revokes all active sessions in the same transaction.

### 3.4 `phone_otp_codes`

The existing table remains conceptually valid, with these final fields:

```text
phone_otp_codes
---------------
id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
phone            VARCHAR(20) NOT NULL
code_hash        CHAR(64) NOT NULL
purpose          VARCHAR(30) NOT NULL DEFAULT 'login'
provider         VARCHAR(40) NOT NULL
expires_at       TIMESTAMPTZ NOT NULL
consumed_at      TIMESTAMPTZ NULL
attempt_count    SMALLINT NOT NULL DEFAULT 0
last_sent_at     TIMESTAMPTZ NOT NULL
created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

Indexes:

```text
INDEX ix_phone_otp_latest (phone, purpose, created_at DESC)
INDEX ix_phone_otp_cleanup (expires_at, consumed_at)
```

OTP rows do not need a user FK because OTP request happens before a verified user necessarily exists.

## 4. User Profile Model

### 4.1 `user_profiles`

```text
user_profiles
-------------
user_id                    BIGINT PRIMARY KEY
work_or_study_field        VARCHAR(255) NULL
education_level            VARCHAR(80) NULL
learning_goal_interests    TEXT NULL
ai_familiarity_level       VARCHAR(50) NULL
daily_learning_minutes     SMALLINT NULL
preferred_career_path      VARCHAR(255) NULL
referral_source            VARCHAR(120) NULL
completed_at               TIMESTAMPTZ NULL
created_at                 TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at                 TIMESTAMPTZ NOT NULL DEFAULT NOW()

FOREIGN KEY (user_id)
  REFERENCES users(id)
  ON DELETE CASCADE

CHECK (daily_learning_minutes IS NULL
       OR daily_learning_minutes BETWEEN 0 AND 1440)
```

Why there is no separate profile ID:

- Each user can have at most one profile.
- `user_id` already uniquely identifies that profile.
- The primary key automatically provides the required user lookup index.
- A second surrogate `id` would not add identity and would allow accidental duplicate profiles.

Profile field ownership:

| Product information | Canonical column |
|---|---|
| حوزه کاری / رشته تحصیلی | `work_or_study_field` |
| سطح تحصیلات | `education_level` |
| هدف از یادگیری و علاقه‌مندی‌ها | `learning_goal_interests` |
| میزان آشنایی با هوش مصنوعی | `ai_familiarity_level` |
| زمان آزاد روزانه | `daily_learning_minutes` |
| مسیر شغلی مورد علاقه | `preferred_career_path` |
| نحوه آشنایی با زیتو | `referral_source` |

Rules:

- Partial profiles are allowed while chat onboarding is in progress.
- Each accepted chat answer updates its canonical profile column immediately.
- `completed_at` is set only when all required product fields are present.
- `profile_builder_answers` is not a second source of truth.
- If raw conversation auditing is later required, it must use an append-only interaction/event table with a defined retention policy.

Indexes:

- No extra index on `user_id`; the primary key already covers it.
- Do not index every profile field.
- Add indexes only after real admin/report queries are defined.
- Candidate future indexes: `education_level`, `ai_familiarity_level`, `referral_source`.

## 5. Course and Version Model

### 5.1 `courses`

```text
courses
-------
id             BIGINT IDENTITY PRIMARY KEY
slug           VARCHAR(120) NOT NULL UNIQUE
title          VARCHAR(255) NOT NULL
domain_code    VARCHAR(120) NOT NULL
status         VARCHAR(30) NOT NULL
created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
archived_at    TIMESTAMPTZ NULL
```

The active version is selected in `course_versions` through `is_active`. Existing enrollments remain pinned to their original version.

### 5.2 `course_versions`

```text
course_versions
---------------
id               BIGINT IDENTITY PRIMARY KEY
course_id        BIGINT NOT NULL FK -> courses.id ON DELETE CASCADE
version_number   INTEGER NOT NULL
status           VARCHAR(30) NOT NULL DEFAULT 'draft'
source           VARCHAR(40) NOT NULL
is_active        BOOLEAN NOT NULL DEFAULT FALSE
published_at     TIMESTAMPTZ NULL
created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()

UNIQUE (course_id, version_number)
PARTIAL UNIQUE INDEX (course_id) WHERE is_active = TRUE
```

State machine:

```text
draft -> in_review -> approved -> published -> archived
```

Rules:

- Published versions are immutable.
- Editing a published course creates a new version.
- New enrollment uses the course version where `is_active = TRUE` and `status = 'published'`.
- Existing enrollment never silently switches version.

---------------------

template_id           SMALLINT NOT NULL FK -> learning_templates.id
stage_number          SMALLINT NOT NULL

```text
knowledge_documents
-------------------
id               BIGINT IDENTITY PRIMARY KEY
title            VARCHAR(255) NOT NULL
status           VARCHAR(30) NOT NULL DEFAULT 'active'
created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
archived_at      TIMESTAMPTZ NULL
```

```text
knowledge_document_versions
---------------------------
id                  BIGINT IDENTITY PRIMARY KEY
document_id         BIGINT NOT NULL FK -> knowledge_documents.id ON DELETE CASCADE
version_number      INTEGER NOT NULL
content             TEXT NOT NULL
source_type         VARCHAR(40) NOT NULL
source_reference    TEXT NULL

UNIQUE (document_id, version_number)
UNIQUE (content_checksum)
```

```text
course_version_knowledge_documents
----------------------------------
course_version_id         BIGINT NOT NULL FK -> course_versions.id ON DELETE CASCADE
document_version_id       BIGINT NOT NULL FK -> knowledge_document_versions.id
is_required               BOOLEAN NOT NULL DEFAULT TRUE
created_at                TIMESTAMPTZ NOT NULL DEFAULT NOW()

```

This design pins a course version to exact document versions. A later KB edit cannot silently change an already published course.

### 7.3 RAG chunks

```text
knowledge_chunks
----------------
id                    BIGINT IDENTITY PRIMARY KEY
document_version_id   BIGINT NOT NULL FK -> knowledge_document_versions.id ON DELETE CASCADE
chunk_order           INTEGER NOT NULL
chunk_text            TEXT NOT NULL
token_count           INTEGER NULL
embedding_status      VARCHAR(30) NOT NULL DEFAULT 'pending'
created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()

UNIQUE (document_version_id, chunk_order)
```

The embedding column/type is intentionally deferred until the vector provider and `pgvector` strategy are approved. Lexical retrieval can use PostgreSQL full-text search during the first implementation.

### 7.4 Tag joins

```text
course_stage_tags
-----------------
stage_content_id   BIGINT NOT NULL FK -> course_stage_contents.id ON DELETE CASCADE
tag_id             BIGINT NOT NULL FK -> tags.id ON DELETE CASCADE

PRIMARY KEY (stage_content_id, tag_id)
INDEX (tag_id, stage_content_id)
```

```text
knowledge_chunk_tags
--------------------
knowledge_chunk_id   BIGINT NOT NULL FK -> knowledge_chunks.id ON DELETE CASCADE
tag_id               BIGINT NOT NULL FK -> tags.id ON DELETE CASCADE

PRIMARY KEY (knowledge_chunk_id, tag_id)
INDEX (tag_id, knowledge_chunk_id)
```

Runtime retrieval constraints:

1. Determine enrollment and pinned `course_version_id`.
2. Determine current `course_stage_contents.id`.
3. Read stage tags.
4. Restrict documents to `course_version_knowledge_documents`.
5. Restrict/rank chunks using the current stage tags and user question.
6. Never retrieve a chunk only because it shares a tag while belonging to another course version.

## 8. AI Policy and the Two AI Roles

Both AI roles call Arvan through the shared client, but they have different prompts, permissions and persistence.

### 8.1 CMS content-generation AI

Purpose:

- Read course brief, selected KB versions and one learning template.
- Generate draft `content_json` matching the template's JSON schema.
- Never publish automatically.
- Save generation metadata.
- Require human approval.

The CMS AI is not called during normal learner interaction.

### 8.2 Runtime supervisor AI

Purpose:

- Explain only the current published stage.
- Answer learner questions using course-version-scoped RAG.
- Evaluate answers using the stage policy/rubric.
- Return structured JSON.
- Write evaluation and interaction records.
- Advance progress only through application transaction rules.

The runtime supervisor cannot modify course content or select an unrelated course.

### 8.3 `ai_policy_versions`

```text
ai_policy_versions
------------------
id                 BIGINT IDENTITY PRIMARY KEY

response_schema    JSONB NOT NULL
model_name         VARCHAR(120) NULL
temperature        NUMERIC(3,2) NOT NULL
status             VARCHAR(30) NOT NULL DEFAULT 'draft'
created_at         TIMESTAMPTZ NOT NULL DEFAULT NOW()
published_at       TIMESTAMPTZ NULL

UNIQUE (policy_code, version_number)
```

Purposes:

```text

```

### 8.4 `course_stage_ai_policies`

This pins each published stage to an exact AI policy version. Prompt changes do not silently alter an existing published course.

## 9. Enrollment and 20-Stage Progress

### 9.1 `user_course_enrollments`

```text
user_course_enrollments
-----------------------
id                  BIGINT IDENTITY PRIMARY KEY
user_id             BIGINT NOT NULL FK -> users.id ON DELETE CASCADE
course_version_id   BIGINT NOT NULL FK -> course_versions.id
status              VARCHAR(30) NOT NULL DEFAULT 'active'
enrolled_at         TIMESTAMPTZ NOT NULL DEFAULT NOW()
started_at          TIMESTAMPTZ NULL
completed_at        TIMESTAMPTZ NULL
updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()

UNIQUE (user_id, course_version_id)
INDEX (user_id, status)
```

The final table does not store `course_id`; it is derivable from `course_version_id`. This removes the current possibility that `course_id` and `course_version_id` refer to different courses.

Progress percentage and current stage are derived from stage progress rows. They are not independent sources of truth.

### 9.2 `user_stage_progress`

```text
user_stage_progress
-------------------
id                  BIGINT IDENTITY PRIMARY KEY
enrollment_id       BIGINT NOT NULL FK -> user_course_enrollments.id ON DELETE CASCADE
stage_content_id    BIGINT NOT NULL FK -> course_stage_contents.id
status              VARCHAR(30) NOT NULL DEFAULT 'locked'
attempt_count       INTEGER NOT NULL DEFAULT 0
best_score          SMALLINT NULL
started_at          TIMESTAMPTZ NULL
completed_at        TIMESTAMPTZ NULL
updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()

UNIQUE (enrollment_id, stage_content_id)
INDEX (enrollment_id, status)
CHECK (best_score IS NULL OR best_score BETWEEN 0 AND 100)
```

State machine:

```text
locked -> available -> in_progress -> completed
                               \-> needs_retry
```

Enrollment creation:

- Creates 20 stage progress rows from the pinned course version.
- Stage 1 is `available`.
- Stages 2-20 are `locked`.

Successful evaluation transaction:

1. Lock current progress row.
2. Save evaluation.
3. Mark current stage `completed`.
4. Mark the next stage `available`.
5. If stage 20 completed, mark enrollment `completed`.

### 9.3 `user_stage_interactions`

```text
user_stage_interactions
-----------------------
id                  BIGINT IDENTITY PRIMARY KEY
stage_progress_id   BIGINT NOT NULL FK -> user_stage_progress.id ON DELETE CASCADE
actor               VARCHAR(20) NOT NULL
interaction_type    VARCHAR(40) NOT NULL
content_text        TEXT NULL
content_json        JSONB NULL
created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()

INDEX (stage_progress_id, created_at)
```

This is the conversation/audit history. It is not the canonical user profile.

### 9.4 `user_stage_evaluations`

```text
user_stage_evaluations
----------------------
id                  BIGINT IDENTITY PRIMARY KEY
stage_progress_id   BIGINT NOT NULL FK -> user_stage_progress.id ON DELETE CASCADE
policy_version_id   BIGINT NOT NULL FK -> ai_policy_versions.id
attempt_number      INTEGER NOT NULL
input_json          JSONB NOT NULL
output_json         JSONB NOT NULL
score               SMALLINT NOT NULL
passed              BOOLEAN NOT NULL
created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()

UNIQUE (stage_progress_id, attempt_number)
INDEX (stage_progress_id, passed, created_at)
CHECK (score BETWEEN 0 AND 100)
```

-------------

## 11. Canonical Data Ownership Matrix

| Information | Source of truth | Must not be duplicated as canonical data |
|---|---|---|
| User identity | `users.id` | manual counters |
| Login identity | `users.phone` | `username`, localStorage user ID |
| Display name | `users.display_name` | `full_name`, profile name copy |
| Profile answers | `user_profiles` | `users.profession`, builder duplicate |
| Course currently offered | the single active published row in `course_versions` | first course/version by ID |
| Published educational content | `course_stage_contents.content_json` | runtime generated replacement |
| Template/UI contract | `learning_templates` | arbitrary stage strings |
| Course KB membership | `course_version_knowledge_documents` | global unscoped retrieval |
| Retrieval concepts | normalized `tags` and join tables | comma-separated tag strings |
| Learner enrollment | `user_course_enrollments` | localStorage course ownership |
| Learner progress | `user_stage_progress` | legacy `user_progress`, independent 25% |
| AI conversation | `user_stage_interactions` | profile table |
| AI grading | `user_stage_evaluations` | unstructured last lesson text |
| Final qualification | `exam_attempts` | client-side score |
| Certificate | `certificates.exam_attempt_id` | duplicated course/user IDs |

## 13. Legacy-to-Canonical Mapping

### 13.1 User mapping

| Current source | Final destination | Rule |
|---|---|---|
| `users.id` | `users.id` | preserve IDs |
| `users.phone` | `users.phone` | normalize and validate uniqueness |
| `users.username` | `users.display_name` | use if non-empty and not a phone |
| `users.full_name` | `users.display_name` | fallback if username unusable |
| `users.profession` | `user_profiles.work_or_study_field` | fallback only |
| current timestamp fields | final timestamp fields | preserve |

Display name backfill precedence:

```text
existing non-phone username
  -> full_name
  -> deterministic temporary label "کاربر {id}"
```

No migration may invent a phone number.

Users with `phone IS NULL` block the final NOT NULL constraint. Before constraint activation they must be:

- matched to a verified phone through an approved flow, or
- exported to a legacy archive and excluded from active accounts.

Production count of phone-less users is unknown until preflight.

### 13.2 Profile mapping

| Current source | Final destination |
|---|---|
| `user_profiles_v2.work_domain` | `work_or_study_field` |
| `user_profiles_v2.referral_source` | `referral_source` |
| `user_profiles_v2.daily_study_minutes` | `daily_learning_minutes` |

## 14. Migration Strategy

No destructive operation is allowed in the first migration.

### Phase A - Preflight

1. Create verified PostgreSQL backup.
2. Record Alembic revision.
3. Count all current tables.
4. Detect duplicate phones.
5. Detect users with null phone.
6. Detect mismatch between enrollment `course_id` and version's course.
7. Detect duplicate or missing stages per course version.
8. Export legacy KB document metadata.
9. Confirm production schema matches expected head.

Any failed invariant stops the migration.

### Phase B - Additive migration

Proposed revision: `20260728_0006_canonical_identity_learning_contract`.

Add without dropping:

- `users.display_name`
- `users.phone_verified_at`
- `users.last_login_at`
- `users.deleted_at`
- canonical profile fields
- `user_sessions`
- `learning_templates`
- tag tables
- versioned KB tables
- AI policy tables
- interaction/evaluation tables
- missing indexes and constraints that do not conflict with existing data

### Phase C - Backfill

1. Backfill `display_name`.
2. Backfill profile canonical columns.
3. Seed exactly 20 `learning_templates`.
4. Map every current stage type to one template.
5. Validate 20-stage uniqueness.
6. Create versioned KB records only after human course mapping.
7. Validate enrollment redundancies.
8. Generate stage progress rows for active enrollments where mapping is reliable.

Backfill must be idempotent.

### Phase D - Application dual-read transition

1. New code writes only canonical fields.
2. Reads prefer canonical fields.
3. Legacy fallback is temporarily allowed only when canonical data is missing.
4. Emit logs/metrics whenever fallback occurs.
5. New user flow uses session cookie and `/api/me/*`.
6. New learning flow uses pinned course version and stage progress.

Do not dual-write indefinitely. Dual-write is only a short migration bridge.

### Phase E - Verification

Verify:

- Active user count.
- Phone uniqueness.
- Display-name coverage.
- Profile row uniqueness.
- Course version stage count equals 20.
- Every stage has a template.
- Every enrollment points to one valid version.
- Every RAG result belongs to the enrolled course version.
- Deleted users cannot log in.
- Admin can restore a deleted user.
- Old endpoints receive no production traffic.

### Phase F - Cleanup migration

Only after an observation window and backup:

- rename `user_profiles_v2` to `user_profiles` or replace it with the canonical table;
- remove `users.full_name`, `users.username`, `users.profession`;
- remove redundant enrollment columns;
- disable and then remove `questions`, `answers`, `user_progress`;
- remove comma-separated tag fields;
- remove `profile_builder_answers` if no audit requirement exists;
- remove legacy global KB only after all documents are mapped or archived.

Cleanup must be a separate Alembic revision.

## 15. Rollback Strategy

Rollback is possible because the first migration is additive.

Before cleanup:

1. Deploy previous application version.
2. Stop canonical-only writes.
3. Keep added tables/columns; they do not break old code.
4. Restore from backup only if data corruption occurred.
5. Never drop canonical data as part of an emergency application rollback.

After cleanup:

- rollback requires a verified backup or explicit reverse data migration;
- therefore cleanup is delayed until production evidence confirms no legacy reads/writes.

## 16. Required Tests Before Schema Activation

Database:

- Alembic upgrade from every existing revision to head.
- Alembic downgrade for the additive migration.
- PostgreSQL integration tests, not only SQLite.
- duplicate phone and null phone preflight tests.
- profile one-to-one constraint.
- soft delete and restore.
- session revocation on soft delete.
- course/version consistency.
- exactly 20 templates and stages.
- published-version immutability.
- stage tag and KB course-version isolation.
- concurrent stage completion.

API:

- OTP creates session only after successful verification.
- `/api/me/*` rejects missing/expired/revoked sessions.
- user cannot access another user's data.
- deleted user receives an unavailable response.
- admin delete is soft delete.
- admin restore preserves history.
- enrollment pins the active published version.
- runtime AI cannot retrieve another course's KB.
- stage completion unlocks only the next stage.

Migration:

- backfill is idempotent.
- canonical values are not overwritten by weaker legacy values.
- no user, enrollment, profile or certificate is lost.
- row counts and checksums are recorded before and after.
